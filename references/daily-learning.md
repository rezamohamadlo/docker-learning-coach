# Daily learning and review

Reza can study 20–30 minutes daily and values visual explanation, summarizing and review. Use a flexible eight-week starting plan; actual evidence determines pacing. Never imply a timer was measured when only estimating.

| Segment | 20-minute session | 25-minute session | 30-minute session |
|---|---|---|---|
| Retrieve previous learning without notes | 3 min | 4 min | 5 min |
| One concept with a useful visual | 5 min | 6 min | 7 min |
| One practical step or independent check | 7 min | 9 min | 11 min |
| Learner summary, then concise correction | 3 min | 4 min | 4 min |
| Save evidence and next checkpoint | 2 min | 2 min | 3 min |

A review-only day replaces new teaching with fresh diagnosis or retrieval. Never require both a three-question ladder and a long lab in one short session. Offer one well-chosen question plus practical reasoning when that fits the budget. If an install/download consumes the session, record the environment checkpoint and resume the lesson next time. Do not count waiting time as demonstrated understanding.

## End every session

Ask for the learner's one-sentence explanation when time allows. Then save and show: three key points, one useful command or diagram, one common trap, and the exact next starting step. Record the learner's explanation separately from the coach summary. A generated summary is not evidence of mastery. Put the recap in the topic note and the current report, preserving prior evidence.

## Spaced retrieval

Maintain a review queue in the roadmap: topic, last evidence date, next due date, evidence link and current gap. After introduction, schedule a brief next-day retrieval; after demonstration, revisit around 7 days later and 21 days later. Use real calendar conversion for dates; without a reliable start date use session-relative checkpoints. Mark reviews overdue only with known dates.

At session start select one or two due items. Ask before showing the answer. Prioritize gaps and prerequisites, not just the oldest item. Failed recall prompts a short correction and a fresh check; keep historical demonstration and add the current retention gap. Reschedule a near-term review. Retrieval success later may earn Retained. Do not ask the same multiple-choice options repeatedly.

Every seventh session is a weekly consolidation: reconstruct the week's visual map, explain a changed scenario, revisit one practical observation, and save a weekly summary with strengths/gaps. At a phase boundary combine this with the phase review; do not add a second large exam. If reviews consume today's budget, defer new content.

## Split the labs

| Work | Daily slices, each within the session budget |
|---|---|
| Setup | OS/shell/context; install or start engine if needed; verify outputs |
| Containers | Run and observe; map ports visually; stop/start and explain; independent variation |
| Build | Read Dockerfile; build/run; inspect identity; change/rebuild/recreate |
| Storage | Predict lifetime; prove persistence; bind-mount comparison; backup; restore and verify |
| Network | Draw host/container boundaries; run name lookup; diagnose changed network |
| Compose | Draw stack; read config; start and inspect; persistence; failure/recovery |
| Capstone | Design; image; Compose/storage; runtime checks; diagnosis; restore; explanation/review |

End each practical slice at a known safe checkpoint. Record directory, relevant file changes, exact lab resource names, stopped/running state, data to retain, and next command. Stop only session-owned services when appropriate; preserve volumes for later work. Never silently leave a resource-consuming lab running simply because the lesson ended.
